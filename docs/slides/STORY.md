# STORY.md — kalo 项目介绍

## ① 用户意图对齐

**目标受众**：技术社区 / 面试官 / 课程评审 —— 看的是「一个学生如何把教学项目做成可维护的工程项目」，因此既要看懂技术，也要看到工程判断力。
**核心目标**：讲完后观众相信三件事：① 这是**真能跑的编辑器**，不是玩具 demo；② 核心技术选型（Piece Table + Treap）有明确的性能收益与代价，且收益被量化过；③ 项目有可复现的质量保障（三层测试 + 四平台 CI）。
**PPT 长度**：14 页。Hero 配额 3 页（封面 / 原理数据页 / 结束页），占 21%，落在 20–30% 区间。
**视觉调性**：终端质感 / 技术克制 / 数据说话 / 深色专业。
**内容边界**：必讲 —— Piece Table 原理与实测数据、权威存储不变式、三套下标、中文排版、测试与 CI、多语言高亮的分阶段计划。不讲 —— 逐行代码推演、AI 参与度的笔墨细节（仅在结束页一句带过）。

## 数据必须落点（每处数据都带判断）

- **3.06x 随机插入加速** → 分块表的价值集中在随机位置的增删，编辑器的真实使用模式恰好就是这种。
- **0.03x 顺序追加** → 反过来看，顺序写场景下分块表是纯负担，所以它不是万能替换，这是选型必须承认的代价。
- **190ms vs 个位数毫秒** → 真正的瓶颈不在存储层而在行视图，重心放错就会做无用优化。
- **18964 断言** → 数量本身不是价值，关键在于它们包含对照 std::string 的随机差分测试，能捕获人眼看不出的错误。
- **0.5% 注释密度 / 815 行原样保留** → 说明项目的设计判断由人做出，AI 承担的是实现与验证工作。
